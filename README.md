# 1부. 왜 이런 게 필요한가

## 1-1. AI에게는 "책상"이 하나뿐입니다

AI는 매번 답을 만들 때, 자기 앞에 놓인 종이들을 전부 읽고 씁니다.
그 책상에 올릴 수 있는 종이의 양이 정해져 있습니다. 이걸 **컨텍스트(context)** 라고 부릅니다.

책상 위에 올라가는 것들:

- 캐릭터 카드 (성격, 말투, 외모)
- 시스템 프롬프트 / 프리셋 (지시사항, 출력 규칙)
- **로어북에서 발동된 항목들**
- **지금까지의 대화 내용**

**중요한 건 이겁니다: 책상 크기는 고정이고, 하나가 커지면 다른 하나는 밀려서 떨어집니다.**

그리고 제일 먼저 떨어지는 게 **대화 내용의 오래된 부분**입니다.

## 1-2. 토큰이 뭔가요

책상 면적을 재는 단위입니다. 영어는 대략 4글자가 1토큰, 한국어는 대략 1글자가 1토큰 남짓.
"컨텍스트 200k"는 책상에 20만 토큰까지 올릴 수 있다는 뜻입니다. 많아 보이지만 금방 찹니다.

## 1-3. 그래서 무슨 일이 벌어지냐면

실제 사례입니다. 제작자의 로어북은 이랬습니다.

```
항목 11개, 전부 "항상 주입" 설정
→ 매 턴 32,593토큰이 무조건 책상에 올라감
```

**매 턴 3만 2천 토큰입니다.** 대화 히스토리가 들어갈 자리를 그만큼 뺏고 있다는 뜻입니다.

그래서 생기는 증상:

- 로어북에는 "3년 전 그 사건"이 빠짐없이 적혀 있는데
- **방금 전 대화**를 까먹습니다. 밀려서 떨어졌으니까요
- 캐릭터가 갑자기 톤이 이상해집니다. 카드와 프리셋 일부도 밀렸으니까요
- "로어북 다 넣었는데 왜 이래?" → **로어북을 다 넣었기 때문에** 이렇습니다

**기억을 늘린 게 아니라, 기억으로 기억을 덮어쓴 겁니다.**

## 1-4. 지금 SillyTavern이 항목을 고르는 방법은 둘뿐입니다

### ① 키워드 매칭

항목에 단어를 등록해두면, 대화에 그 단어가 나올 때 발동합니다.

문제:

- **단어가 안 나오면 안 들어갑니다.** "아버지 이야기"라는 항목에 `아버지`를 걸어놨는데, 대화에서 "그 사람"이라고만 부르면 발동 안 합니다
- **단어만 나오면 들어갑니다.** 지나가는 말로 한 번 언급했을 뿐인데 2천 토큰짜리 항목이 통째로 들어옵니다
- 항목이 70~100개가 되면, 대화가 길어질수록 **걸리는 항목 수가 계속 늘어납니다**

### ② constant (항상 주입)

고르기를 포기하고 전부 넣는 겁니다. 위의 3만 2천 토큰이 바로 이 경우입니다.
빠뜨릴 걱정은 없지만, 대신 책상을 통째로 먹습니다.

## 1-5. Jev Lorebook은 세 번째 방법을 넣습니다

**매 턴, 지금 이 장면에 정말 필요한 항목만 "판단해서" 넣습니다.**

같은 로어북, 같은 대화에서 실측한 결과:

| | 기존 | Jev Lorebook |
|---|---|---|
| 매 턴 주입량 | 32,593토큰 | **3,959토큰** |
| 방식 | 11개 전부 강제 | 후보 20개 회수 → **6개 채택** |
| 추가 지연 | 0 | 2.1초 |
| 추가 비용 | 0 | 턴당 약 $0.0007 (0.1원) |

**주입량이 1/8이 됐습니다.** 밀려났던 2만 8천 토큰이 대화 히스토리로 돌아옵니다.

# 2부. 어떤 원리인가

## 2-1. 기억을 세 층으로 나눕니다

사람의 기억이 한 덩어리가 아닌 것과 같습니다.

### ⭐ 1층 — 코어 (항상 들어감, 800토큰 이내)

**"지금 우리가 어떤 사이인지"** 를 현재형 한 장으로 요약해 둡니다.

```
Relationship: 연인. 3주 전 고백, 서로 인정함.
Dynamics: 그는 여전히 존대를 쓰지만 단둘일 때는 풀어짐.
Ongoing: 아버지 문제로 갈등 중. 아직 해결 안 됨.
Facts: 그는 비를 싫어함. 왼손잡이. 고양이 알러지.
```

이건 **검색 대상이 아닙니다. 무조건 매 턴 들어갑니다.**

왜 필요하냐면 — 검색만으로는 "어제 사랑한다고 말한 사이"라는 사실이 매번 잡히지 않습니다.
대화 주제가 요리면 요리 관련 항목이 올라오고, 연애 상태는 안 올라옵니다.
그래서 캐릭터가 갑자기 남처럼 굽니다. **코어 층이 그걸 막습니다.**

용량이 작아서(800토큰) 항상 넣어도 부담이 없습니다.

### 🔍 2층 — 검색층 (턴당 4,000토큰 예산)

**과거 기록 전부가 여기 들어 있습니다.** 수만 토큰이어도 상관없습니다.
여기서 **매 턴 4,000토큰어치만 골라서** 넣습니다. 이 확장의 본체입니다.

"저장고가 아무리 커도 책상에 올라가는 양은 4,000으로 고정" — 이게 핵심입니다.
로어북을 계속 늘려도 대화가 밀리지 않습니다.

### 📄 3층 — 원문 최근 20개

**최근 대화는 요약하지 않고 원문 그대로 둡니다.**

요약은 정보를 남기고 공기를 지웁니다. 말투, 머뭇거림, 분위기 같은 게 다 날아갑니다.
방금 나눈 대화까지 요약해버리면 캐릭터가 갑자기 딱딱해집니다. 그래서 최근 20개는 손대지 않습니다.

> **정리하면:** 변하지 않는 것은 1층에, 과거 기록은 2층에서 골라서, 지금 이 순간은 3층에 원문 그대로.

## 2-2. 2층은 어떻게 고르나 — 사서와 편집자

두 부품이 역할을 나눕니다.

### 사서 = 임베딩 (벡터 검색)

**임베딩이 뭔가요?**
글의 의미를 숫자 목록으로 바꾸는 기술입니다. 의미가 비슷한 글은 숫자도 비슷해집니다.
그래서 "지금 이 장면"과 숫자가 비슷한 항목을 빠르게 찾아낼 수 있습니다.

**이건 SillyTavern에 이미 있는 기능입니다.** 이 확장이 새로 만든 게 아니라, 있는 걸 그대로 씁니다.
수백 개 항목 중에서 **비슷해 보이는 20개**를 뽑아옵니다. 여기까진 잘합니다.

**그런데 임베딩에는 원리적으로 못 하는 게 두 가지 있습니다.**

**① 반대말을 구분 못 합니다.**

```
"그는 흡혈귀를 사랑한다"
"그는 흡혈귀를 증오한다"
```

이 둘은 임베딩이 보기에 **거의 같은 글입니다.** 쓰인 단어가 같으니까요.
사랑과 증오를 뒤집어 넣어도 검색은 똑같이 걸립니다. 그리고 그게 RP에서 제일 치명적인 오류입니다.

**② 조건을 판단하지 못합니다.**

```
"밤에만 나타난다"
"그 인물이 같은 방에 있을 때만 이 규칙이 적용된다"
```

지금이 낮인지 밤인지, 그 인물이 여기 있는지는 **유사도의 문제가 아니라 판단의 문제**입니다.
임베딩은 "비슷하다/안 비슷하다"만 압니다.

### 편집자 = Jev

그래서 사서가 뽑아온 20개를 **실제로 읽고 고르는 사람**이 필요합니다.

**Jev는 TypeSafe AI가 만든 "판단 전용" 모델입니다.**

- **글을 쓰지 않습니다.** 소설도 대사도 못 씁니다
- **판정만 합니다.** "이게 맞나 / 몇 점이냐 / 셋 중 뭐냐"
- 대신 **빠르고(수백ms~2초) 거의 공짜입니다(턴당 약 0.1원)**

지금까지 소프트웨어가 키워드 매칭이나 "점수 0.25 미만은 버림" 같은 조잡한 방법을 쓴 이유는 간단합니다.
**판단을 시키려면 LLM을 불러야 했고, 그건 느리고 비쌌기 때문입니다.**
Jev는 그 전제를 깹니다. 그래서 "매 턴, 후보 20개를 전부 읽고 고른다"가 현실적으로 가능해집니다.

## 2-3. Jev가 매기는 점수 — 3축

후보 하나하나를 동시에(병렬로) 세 가지 기준으로 봅니다.

**① 모순 위험 — "이게 빠지면 AI가 설정을 어길 위험이 있나?"**

> 예: 지금 장면에 그 캐릭터의 형이 등장했다. "형과는 절연 상태"라는 항목이 안 들어가면,
> AI가 반갑게 인사하는 장면을 써버립니다. → **모순 위험 높음, 반드시 넣어야 함**

**② 장면 적합 — "지금 이 장면에 실제로 쓰이나?"**

> 예: 비 오는 옥상에서 단둘이 대화 중. "옥상은 그의 도피처"라는 항목 → **적합 높음**
> 같은 상황에서 "3년 전 사업 실패 경위" → 지금 안 쓰임 → **적합 낮음**

**③ 최근 중복 — "최근 대화에 이미 나와서 또 넣을 필요 없나?"**

> 예: 방금 대화에서 그 사건을 직접 언급하며 이야기했다 → 요약본을 또 넣을 이유가 없음 → **감점**

최종 점수는 이렇게 계산합니다.

```
(0.6 × 모순위험 + 0.4 × 장면적합) × (1 − 최근중복)
```

**모순 위험에 더 큰 가중치(0.6)를 준 이유:** 설정을 어기는 건 되돌릴 수 없지만,
좀 안 어울리는 항목이 하나 들어가는 건 그냥 조금 낭비일 뿐이기 때문입니다.

점수 0.3 미만은 버리고, **높은 순서로 4,000토큰을 채우고 멈춥니다.**

## 2-4. SillyTavern을 고치지 않습니다

고른 항목은 SillyTavern이 원래 제공하는 **공식 기능**(`WORLDINFO_FORCE_ACTIVATE`, "외부에서 이 항목을 켜라")으로 주입합니다.

- **ST 코드를 한 줄도 수정하지 않습니다.** 업데이트해도 안 깨집니다
- **확장을 끄면 즉시 원래대로 돌아갑니다.** 잔여물이 없습니다
- 기존 키워드 매칭도 그대로 살아 있습니다. 위에 얹는 구조입니다

### 다만, 이 확장이 만드는 항목에는 키워드를 달지 않습니다 (v0.6.0~)

변환·스플릿으로 생성된 항목은 **발동 경로를 Jev 하나로 고정**합니다. 이유는 세 가지입니다.

1. **관측이 안 됩니다.** ST는 키워드 발동을 `console.debug`로만 남겨서, 뭔가 왜 들어갔는지 확인하기 어렵습니다
2. **재귀 연쇄 위험이 있습니다.** 요약 항목의 본문에는 등장인물·장소 이름이 수십 번 나옵니다. 그걸 키로 잡으면 항목끼리 서로를 깨우고, 재귀 스텝 제한(`world_info_max_recursion_steps`)이 `0`이면 제동이 걸리지 않아 예산 상한까지 찭니다
3. **예산이 생니다.** 이 확장은 고른 항목을 토큰 예산 안에서 관리하는데, 키워드 발동은 그 밖에서 별도로 들어옵니다

직접 만드신 항목의 키워드는 건드리지 않습니다. 재귀 차단(`재귀 제외`/`재귀 방지`)도 강제로 켜지 않으니, 키워드를 쓰시는 분은 기존대로 직접 조절하시면 됩니다.

# 3부. 부가 기능 — 손으로 하던 노동 두 가지

## 3-1. [챗→로어북 변환] — 요약을 대신 해줍니다

대화가 길어지면 직접 요약해서 로어북에 넣는 작업, 다들 하실 겁니다. 그걸 버튼 하나로 합니다.

**누르면 일어나는 일:**

1. **마지막으로 변환한 지점 이후의 대화만** 가져옵니다 (처음이면 전체)
2. 메인 API(지금 쓰는 모델)로 요약을 만듭니다
3. 이런 형식으로 강제합니다:
   ```
   ### 2026-09-20 — 옥상에서의 고백

   (요약 본문)
   ```
4. **날짜별로 따로따로** 로어북 항목이 됩니다 (키워드는 달지 않습니다 — 아래 참고)
5. 자동으로 검색 색인에 등록합니다
6. ⭐코어 층을 갱신합니다 (관계가 변했으면 반영)
7. **전부 성공했을 때만** 원본 메시지를 숨깁니다 (최근 20개는 남겨둠)

**왜 날짜별로 쪼개나요?**
통짜 덩어리는 검색해서 고를 수가 없기 때문입니다. 고를 알갱이가 있어야 고르죠.

**왜 원본을 숨기나요?**
같은 내용이 요약본으로도 들어가고 원문으로도 들어가면 두 번 먹습니다. 숨긴 건 `/unhide`로 되돌릴 수 있습니다.

**중간에 실패하면?**
**아무것도 저장하지 않습니다.** 반쯤 들어가서 꼬이는 일이 없습니다. 그냥 다시 누르면 됩니다.

## 3-2. [기존 항목 스플릿] — 이미 쌓인 통짜 로어북 구제

이미 "요약 1", "요약 2" 같은 이름으로 수천~수만 토큰짜리 항목을 쌓아두신 분들을 위한 기능입니다.

통짜 항목은 검색이 무의미합니다. 4,000토큰 예산인데 항목 하나가 1만 토큰이면 고를 방법이 없습니다.

**본문 안의 날짜 헤더를 찾아 자동으로 쪼갭니다.**

실측 결과:

```
항목 11개 → 40개
덩어리 중앙값 924토큰 / 예산 초과 덩어리 0건
```

- 체크박스로 **어떤 항목을 쪼갤지 직접 고릅니다** (기본은 날짜가 2개 이상 있는 것)
- **자동으로 백업 로어북을 먼저 만듭니다**
- **백업 검증에 실패하면 거기서 중단합니다.** 원본을 먼저 건드리지 않습니다

### 여기서 발견한 것 하나 (중요합니다)

제작자 로어북에 "너무 길어서 요약본을 다시 요약한" 항목이 있었습니다. 실제로 비교해봤습니다.

| | 크기 | 쪼개진 덩어리 수 | 예산 초과 덩어리 |
|---|---|---|---|
| 원본 | 20,534토큰 | **15개** | **0건** |
| 재요약본 | 10,724토큰 | 5개 | 1건 |

**재요약본이 더 작은데 더 나빴습니다.**
재요약이 날짜 경계를 뭉개버려서, 검색으로 고를 수 없는 통짜 덩어리를 만들었기 때문입니다.

**검색 기반에서는 "잘게 갈린 원본"이 "뭉개진 요약"보다 낫습니다.**
크기를 줄이려고 요약을 또 하는 건, 오히려 손해일 수 있습니다.

# 4부. 설치와 사용

## 4-1. 준비물

### ① SillyTavern 1.18.0 이상

### ② Jev API 키 (TypeSafe AI에서 발급)

> ⚠️ **폴백이 없습니다.** 키가 없으면 동작하지 않고, 명시적으로 에러를 냅니다.
>
> 일부러 이렇게 만들었습니다. Jev 판정이 이 확장의 전부인데, 실패했을 때 조용히 옛날 방식으로 되돌아가면
> **"잘 되고 있는 줄 알았는데 사실 안 되고 있던" 상태**가 생깁니다. 그게 더 위험합니다.
> 안 되면 안 된다고 말합니다.

비용은 턴당 약 $0.0007입니다. 하루 100턴을 해도 10센트 수준입니다.

### ③ 임베딩 소스 (후보를 뽑아올 사서)

설정에서 12종 중 고릅니다.

- **Gemini 권장** — 품질 좋고 무료 할당량이 넉넉합니다 (Google AI Studio 키)
- **transformers** — 브라우저/서버에서 로컬로 돌아갑니다. **키가 필요 없습니다.** 대신 품질이 약간 떨어집니다

이미 vectors 확장을 쓰고 계셨다면 그 키를 그대로 씁니다.

### ④ Jev로 보낼 통로 (CORS 우회)

브라우저에서 외부 API를 직접 부르는 건 보안 정책상 막혀 있습니다(CORS).
그래서 SillyTavern 서버를 한 번 거쳐야 합니다. **둘 중 아무거나** 되면 됩니다.

**방법 A — 동봉된 `jev-proxy` 서버 플러그인**

`config.yaml`에서 `enableServerPlugins: true` 로 바꾸고 서버 재시작.
(자작 플러그인만 쓸 거면 `enableServerPluginsAutoUpdate: false` 권장)

**방법 B — SillyTavern 내장 CORS 프록시**

`config.yaml`에서 `enableCorsProxy: true`. 플러그인 설치가 필요 없습니다.

> ⚠️ 단, **basicAuth(아이디/비밀번호 로그인)를 켠 서버에서는 이 방법이 동작하지 않습니다.** 인증 헤더가 충돌합니다. 이 경우 방법 A를 쓰세요.

**확장이 세션마다 한 번씩 자동으로 감지해서 되는 쪽을 씁니다.** 현재 어느 경로를 쓰는지 패널에 표시됩니다.

## 4-2. 설치

### 확장 설치 (둘 중 하나)

**방법 1 — SillyTavern 안에서 (권장)**

확장 패널 → `Install extension` → 이 저장소 주소 붙여넣기

**방법 2 — 직접 복사**

```
SillyTavern/public/scripts/extensions/third-party/lorebook-triage/
```

여기에 저장소 내용을 넣고 브라우저 새로고침.

### 서버 플러그인 설치 (방법 A를 쓸 경우에만)

이 저장소의 `server-plugin/` 폴더를 아래 위치에 `jev-proxy` 라는 이름으로 복사합니다.

```
SillyTavern/plugins/jev-proxy/index.js
```

그다음 `config.yaml`에서 `enableServerPlugins: true` 로 바꾸고 서버 재시작.

## 4-3. 첫 세팅 (한 번만)

**1단계. 확장 설정 서랍 열기**

- 확장 켜기
- Jev 키 입력
- 예산 확인 (기본 4,000. 처음엔 그대로 두세요)
- 임베딩 소스 선택 (키 등록 상태가 ✓로 표시됩니다)

**2단계. 대상 로어북 확인 — 기본값 "자동"을 유지하세요**

자동은 **현재 채팅에 물린 로어북 + 캐릭터 카드에 붙은 로어북**만 대상으로 잡습니다.

> ⚠️ 전역 고정 옵션도 있지만 **일반적으로 쓰지 마세요.**
> 한 캐릭터의 기억이 다른 모든 채팅에 주입되는 건 치명적입니다. 다른 캐릭터가 갑자기 모르는 사람 얘기를 합니다.

**3단계. 채팅 하단 요술봉(🪄) → Jev Lorebook 패널 열기**

여기가 조종석입니다.

**4단계. (통짜 로어북이 있다면) [기존 항목 스플릿] 먼저**

쪼개기 전에 색인하면 의미가 없으니 순서가 중요합니다.

**5단계. [색인] 누르기**

로어북 항목들을 검색 가능한 형태로 변환합니다. 항목 수에 따라 몇 초~몇 분.

> ⚠️ **임베딩 소스나 모델을 나중에 바꾸면 반드시 재색인해야 합니다.** 안 하면 검색이 엉망이 됩니다. 경고가 자동으로 뜹니다.

**6단계. 그냥 대화 시작**

이후는 전부 자동입니다.

## 4-4. 평소 사용법

**평소엔 아무것도 안 해도 됩니다.** 매 턴 알아서 골라 넣습니다.

**대화가 쌓였을 때** → 요술봉 패널 → **[챗→로어북 변환]**
증분만 처리하니까 아무 때나 눌러도 됩니다. 하루 끝에 한 번씩 누르는 습관을 들이면 편합니다.

**제대로 되는지 확인하고 싶을 때** → 패널의 **직전 턴 판정 테이블**

```
항목명                     모순  장면  중복  최종   채택
옥상 — 그의 도피처         0.71  0.92  0.05  0.78   ✅
형과의 절연                0.88  0.64  0.00  0.78   ✅
3년 전 사업 실패           0.21  0.11  0.00  0.17   ❌
```

어떤 후보가 몇 점을 받고 뭐가 채택됐는지 전부 보입니다. **F12 개발자 콘솔을 열 필요가 없습니다.**
판정이 이상하면 여기서 바로 보입니다.

**색인 현황** — 항목마다 ✓/✗ 표시. ✗인 항목은 검색에 안 잡히니 여기서 확인하고 재색인하세요.

**[이 로어북을 에디터에서 열기]** — 변환된 항목이 제대로 들어갔는지 바로 확인.

## 4-5. 되돌리기

| 되돌리고 싶은 것 | 방법 |
|---|---|
| 확장 전체 | 설정에서 끄기 → 즉시 원래 ST 동작 |
| 숨겨진 원본 메시지 | `/unhide` |
| 스플릿한 로어북 | 자동 생성된 백업 로어북으로 교체 |
| 설정 파일 | 확장이 변경 전 백업을 남깁니다 |

**ST 코어를 수정하지 않기 때문에 잔여물이 없습니다.** 폴더를 지우면 흔적 없이 사라집니다.

# 5부. 자주 나올 질문

<details>
<summary><b>로어북이 20개 정도인데 저도 써야 하나요?</b></summary>

아니요. 전부 넣어도 예산에 여유가 있으면 그냥 쓰세요. 이건 저장고가 예산보다 훨씬 클 때 의미가 있습니다.
</details>

<details>
<summary><b>예산 4,000토큰은 어떻게 정해진 숫자인가요?</b></summary>

SillyTavern 기본값은 컨텍스트의 25%입니다(200k면 최대 5만). 4,000은 약 2% 수준입니다.
요약 한 덩어리를 250토큰으로 보면 **턴당 13~20덩어리**가 들어갑니다. 실사용에선 충분했습니다. 설정에서 바꿀 수 있습니다.
</details>

<details>
<summary><b>2.1초 느려지는 게 체감되나요?</b></summary>

생성 자체가 보통 10~30초 걸리니 앞에 2초 붙는 정도입니다. 그리고 같은 턴에서 연달아 생성이 일어날 때는 **60초 캐시**가 받아서 다시 안 부릅니다.
</details>

<details>
<summary><b>기존 로어북 설정이 망가지나요?</b></summary>

아니요. 키워드 매칭도, constant 항목도 그대로 동작합니다. 이 확장은 **거기에 추가로** 항목을 켜는 방식입니다.
</details>

<details>
<summary><b>스플릿하면 원본이 날아가나요?</b></summary>

자동 백업을 먼저 만들고, 백업 검증에 성공해야만 진행합니다. 실패하면 원본을 건드리지 않고 중단합니다.
</details>

<details>
<summary><b>변환이 제 말투나 분위기를 망치지 않나요?</b></summary>

최근 20개 메시지는 요약하지 않고 원문 그대로 남깁니다. 요약되는 건 이미 지나간 부분입니다.
</details>

<details>
<summary><b>Jev 키 없이 임베딩만으로는 못 쓰나요?</b></summary>

안 됩니다. 판정이 이 확장의 본체라서요. 임베딩만 쓰실 거면 기존 vectors 확장이 이미 그 일을 합니다.
</details>

<details>
<summary><b>그룹챗에서도 되나요?</b></summary>

채팅에 물린 로어북은 정상 동작합니다. **캐릭터별로 다른 로어북을 물리는 그룹챗 구성은 아직 미지원**입니다.
</details>

# 6부. 알아두셔야 할 것 (솔직하게)

**Jev는 2026년 9월에 나온 신생 API입니다.** 제3자 검증이 없습니다.
회사가 발표한 성능 수치(20~200배 빠름, 40~400배 저렴)는 **자체 발표**이고, 이 글에 적힌 숫자들(32,593→3,959, 2.1초, 후보20→채택6)은 **제작자 환경에서 직접 잰 값**입니다. 환경에 따라 다를 수 있습니다.

**로어북 내용이 외부 API로 전송됩니다.**
판정을 하려면 후보 항목의 본문을 Jev에 보내야 합니다. 로어북에 민감한 내용이 있다면 이 점을 감안하고 쓰세요. 숨기지 않고 먼저 말씀드립니다.

**점수 하한 0.3은 아직 튜닝 중입니다.**
너무 많이 들어오거나 필요한 게 자꾸 빠지면 피드백 주세요. 판정 테이블 스크린샷이 있으면 가장 도움이 됩니다.

**그룹챗 캐릭터별 로어북은 미지원입니다.**
